# DocuSign eSignature Migration Design

**Date:** 2026-03-12
**Status:** Approved
**Scope:** Replace Dropbox Sign with DocuSign eSignature API (Option A — direct replacement)

---

## Overview

Replace the Dropbox Sign integration in the Coast vehicle marketplace with DocuSign eSignature. The existing document generation pipeline (PDFKit) and storage layer (Supabase) remain unchanged. Only the signing layer is replaced.

---

## Architecture

### Authentication — JWT Grant

DocuSign uses **JWT Grant (server-to-server)** rather than a simple API key. The server signs a JWT with an RSA private key and exchanges it for a short-lived access token (1-hour TTL).

**Token caching strategy:** Store the token alongside its `expires_at` timestamp. Before each API call, check if the current time is within 5 minutes of expiry — if so, request a new token. This prevents silent auth failures for long-running server instances.

**One-time consent requirement:** Before the first API call succeeds, a DocuSign administrator must grant consent for the integration key to impersonate the user. This is done once per environment by visiting:
```
https://account-d.docusign.com/oauth/auth?response_type=code&scope=signature%20impersonation&client_id=<INTEGRATION_KEY>&redirect_uri=<ANY_VALID_REDIRECT>
```
For production, replace `account-d.docusign.com` with `account.docusign.com`. Without this step, all API calls return `consent_required`.

**Auth endpoints by environment:**
| Environment | Auth endpoint | Base URL |
|---|---|---|
| Sandbox | `account-d.docusign.com` | `https://demo.docusign.net` |
| Production | `account.docusign.com` | `https://na4.docusign.net` (varies by account) |

The production `DOCUSIGN_BASE_URL` must be obtained by calling `GET https://account.docusign.com/oauth/userinfo` with a valid access token after initial consent. The response contains `accounts[].base_uri` — copy that value into `DOCUSIGN_BASE_URL`. Do not guess the cluster; accounts exist on na2, na3, na4, eu, and others.

**New environment variables:**
```
DOCUSIGN_INTEGRATION_KEY=      # OAuth client ID from DocuSign app
DOCUSIGN_USER_ID=              # GUID of the DocuSign user to impersonate
DOCUSIGN_ACCOUNT_ID=           # DocuSign account ID
DOCUSIGN_PRIVATE_KEY=          # RSA private key PEM (newlines as \n)
DOCUSIGN_BASE_URL=             # demo.docusign.net (sandbox) or na4.docusign.net (prod)
DOCUSIGN_AUTH_SERVER=          # account-d.docusign.com (sandbox) or account.docusign.com (prod)
DOCUSIGN_CONNECT_SECRET=       # HMAC secret for webhook verification
```

**Removed:**
```
DROPBOX_SIGN_API_KEY=
```

Note: The `testMode` flag used in the Dropbox Sign integration has no DocuSign equivalent. Sandbox vs. production is controlled entirely by which environment variables are set.

## Document Sending Flow

1. PDFs generated by PDFKit — **unchanged**
2. PDFs uploaded to Supabase `order-documents` bucket — **unchanged**
3. PDFs converted from `Buffer` to base64 strings via `.toString('base64')` (DocuSign SDK requires `documentBase64` as a string, not a Buffer)
4. DocuSign Envelopes API called with:
   - Document 1: purchase agreement (`documentId: '1'`)
   - Document 2: bill of sale (`documentId: '2'`)
   - One recipient: buyer (signer), identified by name + email
   - Signature and date tabs anchored via text strings embedded in PDFs (see Tabs section)
   - Envelope status `sent` to trigger immediate delivery
5. DocuSign envelope ID stored in `order_documents.esign_ref` for all document rows belonging to the order (same envelope ID on both rows — one envelope contains both documents)
6. Order status updated to `documents_sent`
7. NOTF-03 signing request email sent to buyer (points to Coast order page, unchanged)

## PDF Anchor Text Strings

To position signature/date fields, each PDF will have anchor strings embedded in the signature block area. DocuSign uses these to auto-place tabs.

| Anchor string | Tab type | Document |
|---|---|---|
| `{{BUYER_SIGNATURE}}` | Signature | Both docs |
| `{{BUYER_DATE}}` | Date Signed | Both docs |

These strings are added to `lib/pdf/purchase-agreement.ts` and `lib/pdf/bill-of-sale.ts`, rendered in white text (same color as background, invisible to reader, present in PDF text layer for DocuSign detection).

**Important:** After implementation, tab placement must be verified end-to-end in the DocuSign sandbox before going to production. DocuSign anchor detection can vary depending on PDF structure — do not assume it works without a sandbox test.

## Webhook Flow

**New route:** `POST /api/webhooks/docusign`
**Old route removed:** `POST /api/webhooks/dropbox-sign`

**DocuSign Connect setup (manual, one-time per environment):** In the DocuSign admin console, create a Connect subscription pointing to `https://<domain>/api/webhooks/docusign`. Select `envelope-completed` and `envelope-voided` events. Enable HMAC authentication and note the generated secret — set it as `DOCUSIGN_CONNECT_SECRET`.

**Webhook verification (HMAC-SHA256):**
1. Read the raw request body **before** any JSON parsing
2. Compute `HMAC-SHA256(raw_body_bytes, DOCUSIGN_CONNECT_SECRET)`
3. Base64-encode the result
4. Compare to the `X-DocuSign-Signature-1` request header
5. Return 401 if mismatch

Note: This is different from the Dropbox Sign pattern (which HMACed `event_time + event_type` as hex). DocuSign HMACs the full raw body and base64-encodes (not hex).

**On `envelope-completed`:**
1. Extract `envelopeId` from payload
2. Lookup `order_documents` rows by `esign_ref = envelopeId` (returns both document rows)
3. For each document row, call `getDocument(accountId, envelopeId, documentId)` using the `documentId` stored at envelope creation time — returns a PDF buffer
4. Upload each signed PDF to Supabase storage with `-signed` suffix
5. Update each `order_documents` row: `status = 'signed'`, `signed_at = now()`, `storage_key` updated
6. Update `orders.status = 'documents_signed'`
7. Send NOTF-04 email with signed PDF attachments

**On `envelope-voided`:**
- Acknowledge with 200 response and log the event
- Do not update order status (voiding is out of scope — the `voided` status exists in the schema for future use)
- Prevents DocuSign from retrying indefinitely

**On any other event type:**
- Return 200 immediately (DocuSign retries on non-2xx)

## Document ID Mapping

Each document in the DocuSign envelope must be assigned an explicit `documentId` at creation time so the webhook can retrieve individual signed PDFs:

| Document | `documentId` |
|---|---|
| Purchase Agreement | `'1'` |
| Bill of Sale | `'2'` |

These IDs are constants — they identify documents within a specific envelope, not globally.

## Database

**No schema changes.** The `order_documents.esign_ref` column stores the DocuSign envelope ID in place of the Dropbox Sign envelope ID. The same envelope ID is written to all document rows for an order (one envelope contains all documents). All status values (`pending`, `sent`, `signed`, `voided`) remain valid and unchanged.

## Security

- DocuSign private key stored as env var, never committed
- Webhook HMAC-SHA256 verified against raw body before any processing
- Access tokens cached server-side with expiry, never sent to client
- All DocuSign API calls are server-only (`'use server'` / API routes)

---

## Out of Scope

- Seller co-signing (current system only requires buyer signature — unchanged)
- DocuSign template management UI
- Voiding envelopes programmatically (schema supports it; not yet triggered by any flow)
