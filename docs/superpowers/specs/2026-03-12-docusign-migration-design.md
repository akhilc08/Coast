# DocuSign eSignature Migration Design

**Date:** 2026-03-12
**Status:** Approved
**Scope:** Replace Dropbox Sign with DocuSign eSignature API (Option A — direct replacement)

---

## Overview

Replace the Dropbox Sign integration in the Coast vehicle marketplace with DocuSign eSignature. The existing document generation pipeline (PDFKit) and storage layer (Supabase) remain unchanged. Only the signing layer is replaced.

---

## Architecture

### Authentication

DocuSign uses **JWT Grant (server-to-server)** rather than a simple API key. The server signs a JWT with an RSA private key and exchanges it for a short-lived access token. Tokens are cached in memory and refreshed before expiry.

**New environment variables:**
```
DOCUSIGN_INTEGRATION_KEY=      # OAuth client ID from DocuSign app
DOCUSIGN_USER_ID=              # GUID of the DocuSign user to impersonate
DOCUSIGN_ACCOUNT_ID=           # DocuSign account ID
DOCUSIGN_PRIVATE_KEY=          # RSA private key PEM (newlines as \n)
DOCUSIGN_BASE_URL=             # e.g. https://na4.docusign.net
DOCUSIGN_CONNECT_SECRET=       # HMAC secret for webhook verification
```

**Removed:**
```
DROPBOX_SIGN_API_KEY=
```

## Document Sending Flow

1. PDFs generated by PDFKit — **unchanged**
2. PDFs uploaded to Supabase `order-documents` bucket — **unchanged**
3. PDFs read from storage and base64-encoded
4. DocuSign Envelopes API called with:
   - Two documents: purchase agreement + bill of sale
   - One recipient: buyer (signer), identified by name + email
   - Signature and date tabs anchored via text strings embedded in PDFs
   - Envelope status `sent` to trigger immediate delivery
5. DocuSign envelope ID stored in `order_documents.esign_ref`
6. Order status updated to `documents_sent`
7. NOTF-03 signing request email sent to buyer (points to Coast order page, same as before)

---

## PDF Anchor Text Strings

To position signature/date fields, each PDF will have invisible anchor strings embedded. DocuSign uses these to auto-place tabs without coordinate guessing.

| Anchor string | Tab type | Document |
|---|---|---|
| `{{BUYER_SIGNATURE}}` | Signature | Both docs |
| `{{BUYER_DATE}}` | Date Signed | Both docs |

These strings are added to `lib/pdf/purchase-agreement.ts` and `lib/pdf/bill-of-sale.ts` in the signature block area, rendered in white text (invisible to reader, detectable by DocuSign).

## Webhook Flow

**New route:** `POST /api/webhooks/docusign`
**Old route removed:** `POST /api/webhooks/dropbox-sign`

DocuSign Connect delivers a JSON payload when envelope status changes to `completed`.

1. Verify HMAC-SHA256 signature using `DOCUSIGN_CONNECT_SECRET`
2. Check event type is `envelope-completed`
3. Lookup `order_documents` by `esign_ref` (envelope ID)
4. Call DocuSign Envelopes API to download signed document PDFs
5. Upload signed PDFs to Supabase storage with `-signed` suffix
6. Update `order_documents`: `status = 'signed'`, `signed_at = now()`
7. Update `orders.status = 'documents_signed'`
8. Send NOTF-04 email with signed PDF attachments

## Database

**No schema changes.** The `order_documents.esign_ref` column stores the DocuSign envelope ID in place of the Dropbox Sign envelope ID. All status values (`pending`, `sent`, `signed`, `voided`) remain valid and unchanged.

---

## Dependencies

**Remove:**
```
@dropbox/sign
```

**Add:**
```
docusign-esign       # Official DocuSign Node.js SDK
jsonwebtoken         # JWT signing for auth grant
```

---

## Security

- DocuSign private key stored as env var, never committed
- Webhook HMAC-SHA256 verified before any processing
- Access tokens cached server-side, never sent to client
- All DocuSign API calls are server-only (`'use server'` / API routes)

---

## Out of Scope

- Seller co-signing (current system only requires buyer signature — unchanged)
- DocuSign template management UI
- Voiding envelopes (existing `voided` status kept for future use)
